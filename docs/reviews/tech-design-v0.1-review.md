# starmap 技术设计 v0.1 独立评审

评审对象：`docs/tech-design.md` 初稿（261 行），对照 README 与用户已确认的回答。章节定位以章节号为准；下列行号指评审时的初稿。

评审方式：由未参与初稿编写的独立 AI agent 审查。未执行真实 Codex 开发任务、认证或权限验证，也未运行调度实现。本文提出设计缺口，不声称这些缺口已在代码中发生。

结论：**需要修订后再交作者最终 review**。总体方向符合需求：Python + 文件任务卡 + SQLite、队列驱动、多后端协议、本地独立 Codex 实现与评审，以及 worktree 产物隔离。以下 P1 问题应在开始实现相应模块前关闭。

## 需要修订的问题

### R1 · P1：必要验证失败没有明确的修复路径及预算

- 定位：第 6 节阶段流转（148 行）、第 9 节返工（215 行）、第 10 节故障重试（234 行）。
- 场景：实现结束，框架测试发现功能错误。任务不能进入通过评审，但当前仅“评审要求修改”会回到 implement；测试失败既不是基础设施暂时故障，也未定义是否消耗修复轮次，可能直接悬停或被错误分类重试。
- 建议：明确 verify 失败时分为代码/验收问题与环境/基础设施问题；前者是否重新排队修复、后者如何处理。修复预算以一次新的修改执行开始计数，初次实现不计修复轮次；不能依靠反复失败绕过上限。
- **需要用户决策**：测试失败是否自动交回实现端；是否与评审退回共享已确认的“最多两轮修复”预算。

### R2 · P1：取消与“已预留、尚未启动”之间缺少可执行的握手

- 定位：第 6 节派发第 4–5 步（160–161 行）、第 10 节取消（232 行）。
- 场景：调度器提交额度预留；CLI 将任务移出；调度器随后按之前结果启动 runner。此时旧尝试仍可能开始写代码，取消者也可能找不到尚未写入的进程身份。只比较 generation 无法解决，因为取消并未明确递增 generation。
- 建议：定义 starting 的 CAS、取消意图和 runner 启动许可的握手。预留后取消时不得直接释放未知是否已启动的容量；runner 自己在执行前核对有效授权或启动令牌。明确每个窗口的状态和释放责任，加入故障注入测试。
- 类型：工程设计，可自行修订，无需用户确认算法。

### R3 · P1：实现退出后的验证占槽与工作所有权未定义完整

- 定位：第 4 节 reservations/attempts（89–90 行）、第 6 节角色与容量（148–165 行）、第 9 节验证（209 行）。
- 场景：实现进程退出后释放 attempt 对应槽位，调度器立即派发新实现，同时旧任务执行测试，实际超过总容量。另一种实现会永久保留已 succeeded 的实现额度，导致评审迟迟无法获得共享槽位。当前两种实现都能从文中推导出来。
- 建议：选定执行与验证的配额归属。例如 implement+snapshot+verify 作为一个受监督的工作单元，检查完成后再释放实现额度；评审独立预留。或将 verify 建成明确的独立角色与额度。说明 workspace 准备/集成和结果收集是否计入该工作单元，以及进入评审前何时释放写入所有权。
- 类型：工程设计，可自行修订。

### R4 · P1：人工恢复入口缺失，unknown 与冲突状态不能形成操作闭环

- 定位：第 5 节 CLI（124–140 行）、第 9 节冲突恢复（207 行）、第 10 节 unknown（225–229 行）。
- 场景：unknown 尝试永久保留容量，而 CLI 只有 retry/remove，无法记录“已核对远端停止”并释放占用；冲突由用户处理后，通用 retry 可能从基线重新集成，也可能继续处理已解决的 worktree，语义未定。
- 建议：补充显式 reconcile/resolve 操作或相同语义接口，记录人工依据与操作者；冲突恢复明确保留并验证当前合并状态，从已处理现场继续。仅 CLI 操作不能将“用户说停止了”自动当作强验证，无法核实时应保持风险可见。定义谁可以核对、核对后修改哪些字段、旧结果如何失效。
- 类型：工程设计，可自行修订具体命令；不要把最终权限或风险责任伪装成自动探测。

### R5 · P2：长期排队的基线冻结策略影响真实开发，需要确认

- 定位：第 9 节（203–205 行）。
- 场景：任务夜间执行，但白天入队后主分支已经前进；任务依然在旧 SHA 上实现和验证，交付虽自洽，后续集成成本可能显著增加。另一个边界是多个前置任务分别基于不同时间的主分支，其产物合并引入的变化超出后续任务最初的范围。
- 建议：明确首版承诺只针对冻结基线交付，还是首次派发时解析 base_ref，并记录确切集成基线；不得在验证后隐式追踪变化。限定首次派发后不可漂移的规则，后续追赶主分支必须触发重新验证。
- **需要用户决策**：入队冻结还是首次执行冻结，是否接受“已交付但尚未与最新主分支集成”的结果。

### R6 · P2：修改已排队任务必须重建下游链，是未确认的产品限制

- 定位：第 5 节（140 行）、依赖 revision 固定（88 行）。
- 场景：A→B→C 已入队，用户通过对话 AI 调整 A 的需求。方案要求取消 A 并创建 A2，同时 B 的依赖不可改，因而 B、C 也必须取消并重新创建。对于以 AI 生成任务卡为主的入口，这是明显的操作行为选择，不能只以“禁止隐式变更”替代说明。
- 建议：首版可以保持不可变任务，但要明确给 AI 的操作流程和受影响任务提示；或提供只针对未开始任务的显式修订并使相关约定失效，复杂度较高。
- **需要用户决策**：是否接受首版以取消及重建受影响依赖链处理需求变更。无需现在实现完整任务编辑器。

### R7 · P2：持久化完成与产物文件的提交协议尚未明确

- 定位：第 4 节 SQLite 唯一事实来源（79 行）、artifacts（91 行）、第 9 节交付（213 行）。
- 场景：数据库已记录 delivered 并解锁下游，artifact manifest 或评审文件尚未完成落盘；或进程在先写清单后提交数据库前崩溃。源码 SHA 仍存在，但证据或规则快照无法读回，不能满足任务的可追溯交付条件。
- 建议：定义文件落盘、校验、原子发布、数据库状态转换的顺序。可重建元数据以数据库为准，不可重建日志和证据在写入完成并校验后才能提交交付事务；保留 orphan 清理及启动核对策略。产物引用必须受任务/尝试/版本约束，不能盲信模型返回的路径。
- 类型：工程设计，可自行修订。

### R8 · P2：AI 返回结果与 review verdict 尚缺少稳定契约

- 定位：第 7 节 collect（176 行）、第 8 节 schema（189–191 行）、第 9 节通过/返工（213–215 行）。
- 场景：独立评审输出的“通过但有建议”或“无法判断”如何处理未定义；JSON 可通过结构验证，但 task revision、候选 SHA 不匹配，仍可能被业务层误当成批准。实现结果对“无代码修改但验收已满足”的任务也未说明。
- 建议：给出最小结果类型，区分 pass、request_changes、unable_to_review；绑定 task/revision/attempt/candidate。pass 不覆盖必需验证，unable_to_review 不计为一次已完成的代码修复。明确定义 no-op 产物的处理，至少能明确拒绝而不悬停。
- 类型：工程设计，可自行修订；无需询问具体字段名。

### R9 · P2：对外文档仍将已确认决策写成待定

- 定位：README 的“当前状态与实施路线”末段；docs/design.md 与 docs/roadmap.md 中的待定条目。
- 场景：作者看到技术设计已选 Python/SQLite/本地 Codex，而 README 仍称技术栈、存储及首个接入平台未定，难以判断哪些是用户决策、哪些只是草案。
- 建议：同步已确认项，README 链接本技术设计；“尚未实现”与“尚未选择”分开表述。
- 类型：文档一致性，可自行修订。

## 已有设计中应保留的约束

- 不把未知远端状态误判为失败，不承诺跨进程 exactly-once。
- 非抢占式插队不绕过依赖、时段与容量。
- 独立会话评审与模型服务商选择分离，结果关联候选版本。
- worktree 不是恶意代码的安全隔离，首版限定可信本机项目。
- 通过本地提交及祖先关系处理前置产物，避免钻石依赖重复应用补丁。
- 真实 Codex 调用、认证、非交互审批和取消能力仍需 smoke test，CLI help 只能证明 flags 存在。

## 建议向用户确认的三项问题

1. 必要测试失败是否自动修复，是否与评审返工共用两轮预算？
2. 任务基线在入队还是首次执行时冻结？是否接受交付版本暂未集成最新主分支？
3. 首版需求变更是否可以采用取消旧任务并重建受影响下游链？

其余问题应作为工程修订完成后复核，不应把内部算法或字段命名的决定转交用户。

### R4 剩余缺口：冲突恢复后不能跳过尚未集成的前置产物

第 9 节目前描述冲突解决后保存本地集成提交并“从 implement 继续”。若任务依赖 A、B、C，集成 B 时发生冲突，解决 B 并不意味着 C 也已集成。直接转入实现会在缺失前置代码的基线上工作。

建议持久化确定的集成计划、当前游标、已完成的依赖 SHA 及冲突父提交。解决当前冲突后继续余下合并；全部完成后检查所有要求的前置提交已纳入当前基线，再允许进入 implement。人工处理期间禁止调度推进同一工作区；解决失败或再次冲突仍留在准备阶段。此为工程补充，不需要用户决策。

### R9 剩余文字

- `docs/roadmap.md` 第 2 节仍称“选择一个公司 AI 平台或远端 VM Agent 作为首个实现端”，应改为已经确认的本地 Codex；其他后端作为后续扩展。
- README 的调度能力后仍将非抢占及分别限流描述为待定建议，应注明已确认，取消实现细节仍待落地。
- 设计说明中已经确认的规则与交付语义如保留“建议”措辞，应说明技术设计中的确认项优先，避免让作者重新判断。

修订剩余两项后，工程设计可以进入实现准备；R1/R5/R6 与作者最终 review 仍是独立的未完成事项。

## 第三轮：最终设计复核

结论：**初审 R1–R9 均已在设计层关闭，可以交作者最终 review。当前没有必须继续询问用户的产品决策。** 本结论不代表实现已验证；真实 Codex smoke test、故障注入和调度不变量测试仍按技术设计的验收计划执行。

本轮核对结果：

- **R1**：第 1、6、9 节已写入用户确认的共享两轮预算。初次实现不计轮次，修复派发时事务计数，基础设施重试和显式 retry 不清零预算；测试/环境问题无法可靠分类时转人工。
- **R5**：第 1、5、9 节统一为首次派发冻结本地基线，显式 SHA 固定，不自动 fetch；后续修复和恢复不漂移，也不承诺已经集成最新主分支。
- **R6**：第 1、5 节记录作者接受取消旧任务并重建受影响下游链；移出不隐式级联取消或重写依赖。
- **R4 剩余项**：第 9 节已加入确定的合并计划、游标和逐步 SHA，解决当前冲突后重新取得额度并继续剩余计划；只有全部前置提交祖先检查通过才开始编码。
- **R9 剩余项**：README 已明确非抢占与分别限流为已确定方案；路线图将本地 Codex 写为首个后端。少量历史说明仍用“建议”描述同一方向，但不再形成相反行为，具体方案以技术设计中已确认表为准，可在最终编辑时统一措辞。
- **R2/R3/R7/R8**：取消启动窗口、实现与验证占槽、证据先持久化再事务交付，以及结果 envelope/评审 verdict 的修订均保留，未发现回退。

独立评审建议在作者 review 后按阶段实现，先通过 mock 与故障注入建立队列正确性，再引入真实模型调用。实现中若平台接口或权限与假设不符，应记录差异；影响产品行为时重新询问作者，工程适配细节自行修订。
