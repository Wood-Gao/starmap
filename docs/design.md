# starmap 设计说明

## 需求依据与当前状态

本设计依据最初提供的四张设计照片及后续需求澄清整理。后续澄清确定：项目分为全局 Rules 与开发框架两部分，开发框架以队列为核心，通过实现端执行任务，并由独立第三方 AI 会话评审。并行开发、利用峰谷计价和 24 小时持续开发是主要目标。

当前仅有文档，无可运行实现。下文将已确定的需求与建议的实现语义分开记录。

首版具体方案与已确认决策见[技术设计](tech-design.md)。后续确认采用 Python、JSON 任务卡与 SQLite，本地 Codex 实现及独立评审，独立 worktree 和本地提交/集成。测试与评审共享最多两轮自动修复；首次派发时冻结本地基线，不自动 fetch；修改约定采用移出并重建依赖链。下文早期建议与这些确认项有重叠时，以技术设计中的已确认决策为准。

## 已确定的项目边界

### 全局 Rules

全局规则适用于使用 AI 的日常工作，可以独立于队列框架使用。主要原则包括：

- 依据实际证据判断结果，区分事实、推断及未执行的检查。
- 目标、范围和授权明确时自主执行，边界发生变化时重新对齐。
- 工作流程与风险匹配，简单任务保持轻量。
- 失败后先记录现场和原因，再选择恢复方式。
- 保留验收、评审和交付记录，遵守工程约束，安全使用凭据。

项目规则和任务技能在全局规则之上补充工程细节。例如前端交付技能需要检查用户任务、页面与 API 的协作、功能及交互质量，并在真实浏览器中验证。

### 队列驱动的开发框架

- 新开发任务进入队列，由调度器统一安排。
- 支持最大并发控制、任务依赖、插队和移出队列。
- 实现端可以是公司的 AI 开发平台或远端虚拟机中的 AI Agent。
- 执行层抽象是核心设计：通过统一协议适配不同模型、机器和平台，支持多种执行场景。
- 实现结果必须交由独立于实现会话的第三方 AI 会话评审。
- 目标是并行推进开发、利用峰谷计价、支持长时间持续运行。

独立会话不自动等于不同模型或不同服务商，具体接入方式尚待确定。

## 执行层抽象（接口设计建议）

### 分离模型、运行环境和适配器

- **模型配置**：模型标识、参数和服务来源；平台托管且不开放选择时允许记录为平台管理。
- **运行环境**：机器或容器、工作区、运行时、网络与仓库访问范围，以及资源池。
- **执行后端**：一个可被调度的 Agent 或平台配置，关联运行环境、可用模型和能力声明。
- **适配器**：对接后端的调用协议，转换任务输入、外部状态、产物和错误。
- **执行尝试**：一次实现、修复或评审的具体运行，固定记录所用后端、模型及环境，便于追溯。

开发执行需要模型之外的工具、工作区和运行时。仅能调用模型生成文本的后端不能被视为自动具备仓库修改和测试能力。

### 统一执行契约

以下操作是语义约定，尚未确定语言接口或传输协议。

| 操作 | 统一语义 |
| --- | --- |
| 描述能力 | 返回支持的任务角色、模型、工具、访问范围、容量与可选操作 |
| 提交执行 | 接收任务约定版本、阶段、上下文、产物引用、规则和请求标识，返回执行句柄 |
| 查询状态 | 将外部状态映射为统一状态，保留原始状态；无法确认时返回未知并待核对 |
| 收集结果 | 返回代码版本、产物引用、验证证据或结构化评审意见，以及失败原因 |
| 请求取消（可选） | 区分已收到取消请求与已确认停止；不支持时明确返回能力限制 |
| 恢复会话（可选） | 声明是否支持同一会话接续及所需上下文；不支持时可重新创建执行尝试 |

提交响应丢失时需要通过请求标识核对是否已经启动。若后端无法幂等提交或按标识查询，适配器必须暴露该限制，调度器将该尝试保留为待核对状态，避免盲目重发。

产物引用还要描述后续执行端如何访问。某台 VM 上的本地路径不能直接视为另一平台可读取的产物，必要时通过明确授权的仓库或产物存储传递。

### 能力匹配与后端选择

先根据任务角色、必需工具、运行时、仓库及网络权限、允许的模型和后端范围筛选，再考虑优先级、可用容量、执行时段和成本偏好。硬性约束不因价格或空闲容量被放宽。

无匹配后端时记录阻塞原因。平台不开放模型选择时，不能声称满足指定模型的硬性要求。多个后端共享机器、账号或配额时，通过资源池共同约束容量。

实现、修复和评审复用执行协议；评审使用独立会话和适用的工具权限，记录评审输入及版本。独立会话的识别和验证由适配器提供相应依据。

切换后端是一次明确的重试或重调度决定：先确认旧执行终止或隔离其写入影响，再传递产物和上下文并建立新的尝试。不得假定不同模型或机器之间可以透明迁移会话、权限或文件。

## 建议的调度语义（待实现验证）

### 队列与依赖

逻辑队列保存所有未结束任务，调度器从符合条件的任务中选择工作。任务需要同时满足依赖、执行时段、实现端能力和可用容量等条件，才可以派发。

- 依赖使用有向无环图表示，提交或修改依赖时拒绝循环、自依赖和不存在的任务引用。
- 建议默认以前置任务完成独立评审并满足约定交付条件作为依赖满足的依据。
- 依赖同时关联产物位置和版本；仅有“完成”状态不足以让后续任务获得可用代码。
- 前置任务失败或被移出时，后续任务保留并标记阻塞原因；不静默解除依赖或级联删除。
- 同一目标分支的产物集成需要单独管理，避免并行任务互相覆盖。

### 并发与派发

- 分别配置实现与评审的并发额度；共享同一资源池时，还需共同遵守资源总上限。
- 从选择任务到占用容量必须保持一致，避免多个调度循环重复派发。
- 记录执行 ID 和外部任务 ID；不以一次网络请求超时认定远端任务未启动。
- 重启或失联后先核对远端状态；状态未知的执行仍占用容量，直至核实或通过明确恢复策略处理。
- 使用租约、心跳或其他机制识别异常执行，具体方案待技术选型后确定。

### 插队与移出

- 建议第一版采用非抢占式插队：改变待调度任务的顺序，不打断运行中的工作。
- 插队仍须满足依赖、容量及明确配置的时段策略。
- 对尚未派发的任务，移出意味着停止派发并保留历史记录。
- 对运行中的任务，取消需要实现端支持及停止确认；确认前不能直接释放容量。
- 取消后到达的旧结果保留用于审计，不自动将任务改回完成或解锁依赖。
- 优先级排序的稳定规则及避免低优先级任务长期饥饿的策略，需在实现前明确。

### 峰谷时段与持续运行

- 第一阶段采用显式配置的价格时段、时区、运行窗口和并发策略，不预设具体平台价格。
- 允许延后的任务可以等待低价窗口，紧急任务使用明确的时段例外策略。
- 时段切换建议先作用于新派发任务，不默认终止正在运行的任务。
- 长任务可能跨越价格窗口，不能把“低价时段启动”直接等同于整次执行都按低价计费。
- 持续运行需要持久化状态、异常恢复、重试退避及有限返工机制，避免单个失败任务阻塞整个队列或无限消耗资源。

## 实现与独立评审

实现端接收任务约定、代码上下文和规则，输出代码产物、版本、验证结果及未完成事项。适配层负责提交、查询、结果收集，以及在支持时请求取消。

评审在独立 AI 会话中开展，输入包括任务约定、验收条件、变更差异、必要的代码上下文和实际验证证据。评审意见需要关联任务约定版本及产物版本，并明确问题和是否允许交付。

- 实现会话不能自行充当独立评审者。
- 评审通过也不能代替缺失的必要测试、CI 或交付授权。
- 评审要求修改时，将意见交回实现端，通过队列安排新一轮修复。
- 设置最大返工次数；达到上限、需求有歧义或出现授权问题时转人工处理。
- 代码变化后重新判断测试和评审证据是否有效，禁止直接复用旧版本的完成结论。
- 用已提交版本标识最终产物，并核对验证前后的提交和工作区状态。

## 建议的数据概念

| 概念 | 主要内容 |
| --- | --- |
| 任务约定 | ID、版本、目标、仓库、修改边界、验收条件、交付权限 |
| 调度信息 | 依赖、优先级或位置、执行窗口、实现端要求、阻塞原因 |
| 执行尝试 | 任务 ID、实现或评审阶段、尝试 ID、外部执行 ID、时间、状态、失败原因 |
| 执行后端 | 适配器类型、环境、模型配置、能力、资源池及可用时段 |
| 产物 | 提交、分支或 MR/PR、前置产物版本及集成方式 |
| 验证与评审 | 任务约定版本、代码版本、命令、退出码、日志、评审意见 |
| 调度事件 | 入队、插队、移出、派发、取消、重试、恢复及操作者 |

任务验收结论、产物状态、执行尝试状态和调度阻塞原因分别管理。正式状态机与存储格式尚未确定。

## 后续实现选择

1. 首个实现端和评审端确定为本地 Codex；其接口核对、能力声明及第二种验证用后端按技术设计推进。
2. 技术栈确定为 Python、JSON 任务卡与 SQLite；具体部署及运行配置在实现阶段确定。
3. 并发配置的范围、资源池划分，以及优先级排序策略。
4. 前置任务的交付条件、分支集成方式和冲突处理流程。
5. 计价窗口、时区、紧急任务策略及返工上限。
6. 原有代码是否需要接入，以及许可证与公开发布范围。
