# 提案：任务范围判断与自动恢复

状态：讨论稿。作者已明确执行端可先完成实现、在验收时审查实际范围，不要求中途反向申请。自动恢复的权限与预算仍待确认。本文补充现有 v0.1 技术设计，尚未实现。

## 1. 三个痛点及原因

| 痛点 | 现有设计的不足 | 建议方向 |
| --- | --- | --- |
| 实现端做预期外工作 | 只检查路径，不能识别同一文件内新增功能、无关重构或外部操作 | 同时约束目标、明确非目标、权限和必要改动 |
| 必要改动超出预估范围 | allowed_paths 将不完整的实现预测当成绝对边界 | 分离预计范围与硬边界，完成实现后审查必要性，记录接纳依据 |
| rebase 后任务因 SHA 不匹配卡住 | 将产物定位变化直接作为无法处理的异常，恢复过早依赖人工 | 自动收集现场、诊断差异、重建映射并重新验证 |

需要的是能判断必要性和恢复路径的协作流程，同时保留确定性的权限、版本和状态检查。仅更换更强模型不能替代这些机制。

## 2. 任务卡：目标、硬边界与预计范围

建议分别表达：

- **目标与验收条件**：用户要完成的行为以及通过依据。
- **非目标**：本任务不增加的功能、不做的整理或重构。
- **硬边界**：明确禁止的路径、操作、权限和外部影响；只有原授权方才能调整。
- **预计范围**：预计修改的模块或路径，用于执行计划与异常检测，不自动等同于硬禁区。
- **必要配套改动策略**：独立验收可接纳哪些实际范围偏离，以及何时返工或升级。

现有 allowed_paths 不能在升级时自动降为预计范围，原有明确授权必须保留。新任务卡需要显式选择哪些是硬约束、哪些是计划预测。forbidden_paths 仍是硬边界。

例如“为接口增加字段”可能必须同步调整类型定义、调用方和测试，执行端可以一并实现，由验收者根据真实改动判断必要性；顺手改造整套请求框架则需检查为何原目标无法以更小改动完成。即使文件在允许目录中，也不意味着新增功能或执行部署获得授权。

### 执行端无感知，框架在结果侧接管

不要求实现端安装 starmap、理解任务卡协议、提交范围申请或等待审批回调。适配器将任务目标、非目标及必要约束转换为后端能够接收的输入；执行端按其原有工作方式完成任务。框架保管任务身份、版本和状态，并在执行结束后收集代码、日志及可得结果。

1. 执行端先在任务工作区实现并产出结果，不因超出预计路径而强制暂停。
2. 适配器收集真实基线、候选版本、差异、检查与可得日志；缺少执行端解释时，由框架和评审会话分析，不能把填写范围报告作为接入前提。
3. 独立评审结合目标和验收条件，检查偏离的必要性、改动规模、额外行为与验证覆盖。路径差异是审查线索，不是自动拒绝条件。
4. 必要且适度、未突破硬边界的配套改动可以直接接纳；无关功能或不必要重构提出明确返工意见；证据缺失先由框架收集或重新验证。
5. 保存实际改动范围、评审依据、接纳或退回结论及新增检查。结果在验收完成前保持为候选，不向下游作为已交付产物发布。

评审不能仅凭执行端声称“必要”接纳改动，也不能仅凭文件不在预计清单就拒绝。拒绝意见应指出具体违背的目标或约束、可观察的额外行为或风险，以及需要修正的内容；只有原任务存在实质歧义时才请求作者判断。

先实现后验收适用于隔离工作区中的候选代码。密钥暴露、部署、删除外部数据等不可逆影响无法靠事后拒绝代码撤销，应由执行环境及后端权限限制；不要求实现端配合特定回调协议。后端无法提供所需约束时，适配器必须显式声明限制，不能把交付检查描述成执行隔离。

保留原始任务卡不变，实际范围和验收结论是独立记录，不追改任务卡来假装从未偏离。目标、验收标准、依赖和硬授权均不改变时，接纳必要配套改动不需要重建任务链。改变这些内容仍遵循已确认的移出重建策略；既有 allowed_paths 是否为硬限制须按原任务授权解释，不能自动降级。

## 3. 版本判断：SHA 是定位，证据需要判断适用性

保留旧产物和证据，不原地改写“评审通过的 SHA”。新提交创建新候选与映射记录，记录旧/新基线、旧/新 head、代码树、差异、工具结果及原因。

| 观测 | 处理建议 |
| --- | --- |
| SHA 不同，完整代码树相同 | 候选内容一致；继续检查任务约定、依赖、规则、工具链与测试环境是否兼容，再决定证据能否承接 |
| 任务补丁相似，但基线或完整代码树变化 | 只能作为诊断线索；对新候选重新执行必要测试及独立评审 |
| 有冲突处理、额外修改、补丁遗漏或无法对应 | 分析新差异，保留旧产物，不标为等价；原授权内可提出修复方案 |
| 无法排除代码丢失、外部改动归属不明 | 暂停写操作，保留证据并升级处理 |

Git 的 patch-id 可以辅助识别重复补丁，但其匹配不是对运行结果和业务等价性的证明；尤其不能据此认为新基线上的测试仍通过。依据见 [git-patch-id](https://git-scm.com/docs/git-patch-id)、[git-rebase](https://git-scm.com/docs/git-rebase) 和 [git-diff](https://git-scm.com/docs/git-diff)。

首版建议采取易验证的策略：发现重写后先自动定位并建立映射，再在固定的新候选上重跑必要验证与独立评审，以减少人工接力。更细的证据复用可以以后优化；不能为省测试费用降低交付条件。

下游尚未开始时，只有新候选完成验证后才能按策略更新其产物绑定；下游已开始时保留实际读取的版本，不静默替换其依赖。若需要迁移下游，另行生成影响分析及重新验证计划。

自动处理外部已发生的 rebase，不等同于允许框架自行 rebase 或重写用户分支。框架能否主动执行 Git 写操作受恢复授权约束，不产生推送或强推权限。

## 4. 在转人工前增加诊断与恢复

现有路径可以从“异常 → needs_attention”扩展为：

```text
异常 → 收集确定性现场 → 独立 AI 诊断 → 策略核对
                                     ├─ 原授权内且证据足够 → 执行恢复计划 → 重新验证 → 继续队列
                                     └─ 需新授权或仍有实质歧义 → 向作者提出具体问题
```

建议增加 recovery 模块，复用现有执行后端协议，为诊断会话提供：任务卡、实际范围与验收记录、执行日志、旧新 Git 状态、验证与评审记录、阻塞原因。输出结构化 diagnosis、evidence、proposed_actions、required_permissions 和 expected_postconditions。

诊断会话默认只读；恢复动作必须由框架验证权限并执行，不能把 AI 返回的任意 shell 文本直接当作控制命令。恢复计划固定输入版本，执行前再校验现场；现场变化则重新诊断。恢复后使用新尝试和新 generation，拒绝旧回调覆盖新结果。

可自动处理的例子是重新定位候选、发现证据记录过期后重新验证、在明确支持的后端上核对运行状态。不能靠模型推理证明未知进程已停止；unknown 写入者未排除时，不启动新的代码写入。

诊断、范围审查及恢复使用独立会话、队列和现有共享资源上限。可以让 review 资源池承担只读诊断，涉及写操作时申请实现槽位；不得绕过最大并发。需要可配置的恢复次数、耗时和费用预算，防止“诊断失败再找另一个 AI”无限循环。

现有两轮代码修复预算不自动重置。重新验证、环境恢复与实际改代码分别记账；若恢复计划需要修改实现以满足验收，仍计入代码修复预算。取消任务、硬禁区和权限升级不能通过诊断流程绕开。

## 5. 对现有架构的影响

| 部分 | 调整 |
| --- | --- |
| 全局 Rules | 先区分必要配套改动与目标扩张；先诊断可恢复问题，再向作者升级 |
| contracts | 增加非目标、硬边界、预计范围、实际范围验收记录及恢复策略；不增加执行端反向申请要求 |
| review | 完成实现后审查必要性、实际范围及目标满足情况，偏离预计路径不自动拒绝 |
| verification / artifacts | 增加新旧候选映射、证据适用性判断与重新验证记录 |
| recovery（新增） | 独立诊断、恢复计划、策略检查、结果核对和升级 |
| scheduler / backend | 保留核心结构，由适配器承接输入与产物收集；增加诊断角色的调度及资源、预算约束 |

这属于任务契约、评审及恢复流程的增强，无需重做队列、DAG 或可插拔执行协议。实现仍可保持 Python、JSON 任务卡与 SQLite。

## 6. 建议增加的验收场景

1. 在允许目录中增加无关功能，评审仍能指出目标扩张。
2. 必须修改未预估的类型文件，执行端先完成；独立评审核实必要性和验证后直接接纳。
3. 不支持 starmap 协议或范围回调的后端，也能完成实现与事后验收。
4. 执行端以“必要”为由修改明确禁区，验收不自动放行；涉及外部影响时不能声称事后检查已提供保护。
5. 仅提交身份变化时，自动核对内容与上下文，不直接升级人工。
6. 补丁相似但新基线改变行为时，重跑测试能阻止错误交付。
7. 新候选验证失败，旧通过结论仍保留但不适用于新候选。
8. 诊断发现旧进程可能仍活着，不能释放占用并启动新写入者。
9. 恢复达到预算、出现需求变化或无法排除丢代码时，向作者提出有证据的具体问题。
